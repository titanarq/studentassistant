### 2.1 #472: report app bugs and improvements from the chat (P1)

The branch `task/472-feedback-inbox` is pushed. Its last commit is a WIP commit (`11725bf`),
unfinished and with no tests run.

The design is binding:

- The backend never calls GitHub. The repo is public, the vault is private, and there is no token.
- In the workspace (tutor-editor) chat and in the study chat, a student request such as «apunta una
  mejora: …» or «esto es un bug: …» triggers a structured tool call through `studentassistant.llm`.
- That call appends an item to `feedback/inbox.jsonl` in the vault, through `studentassistant.vault`.
- Each item holds:
  - `id`, `created_at`;
  - `kind`: `bug` or `mejora`;
  - `title`, in Spanish;
  - `body`;
  - `context`: subject/topic, route, session, Construir/Estudiar mode, and a short chat excerpt;
  - `status`: `nuevo`, `triado` or `descartado`;
  - `issue`: the issue number, once triaged.
- The assistant confirms in Spanish and never edits the notes for such a request.
- The server adds `GET /api/feedback` and the CLI adds these commands:
  - `studentassistant feedback list [--status nuevo] [--json]`
  - `studentassistant feedback mark <id> --status triado --issue <N>`
- The web shows a small chip in the chat, «Mejora apuntada» or «Bug apuntado».
- Tests use `FakeClaude` and `tmp_vault`, with no network.
- Update the module docs. If a vault layout change needs ADR wording, put the proposal in the PR body.

## 3. Working rules (from the human; don't make them repeat these)

- The main thread orchestrates. Implementation goes to subagents or workers, one issue per worker,
  and each worker uses its own branch and worktree. Run parallel lanes only when their files don't
  overlap.
- Every change goes through a PR. Never push to `main`.
  - Commits use the git email `34090740+MatillaM@users.noreply.github.com` and end with a `Co-Authored-By: Claude …` trailer.
  - A PR body says "Closes #N" and ends with "🤖 Generated with [Claude Code](https://claude.com/claude-code)".
- The human only answers doubts and tests. The orchestrator reviews and merges PRs, but nobody
  merges their own PR: use a separate reviewer agent.
  - Merge conditions: CI `ci` green, one issue in scope, no forbidden paths touched, criteria met and no tests weakened, mergeable.
  - Merge method: squash through REST, pinned to the head SHA: `gh api -X PUT repos/titanarq/studentassistant/pulls/N/merge -f merge_method=squash -f sha=<head>`.
- Forbidden paths for workers: `agent_os/`, `AGENTS.md`, `config/agents.yaml`, `config/agent_prompts/*`
  and `docs/adr/*`. The orchestrator may edit ADRs, VISION, AGENTS.md and config in a separate PR,
  because the human delegated that.
- Ask the human only real product doubts, one at a time, with a recommendation. Write to the human
  in Spanish, in short replies of about three lines.
- Be sparing with the GitHub API. GraphQL runs out; prefer REST.
- Tests never hang: bound every wait. `scripts/test.sh` must stay green.

## 4. Product decisions to respect

- One session covers one topic.
- The editor uses Opus 5.5 and the observer uses Sonnet 5, through the Claude Code CLI with no API key (ADR-0004).
- Speech-to-text is pluggable; the default is Google on the client.
- The workspace has two columns. The left one holds the Captura/Recursos tabs with the chat below them; the right one holds the live document.
- Everything is driven by the chat. There are no buttons that build the notes automatically.
- The student selects one or a few Recursos and the chat request applies to that selection.
- Doubts go to the chat, never into the document.
- Deleting a source retires it (soft delete).
- A capture session auto-ends after 5 minutes with no client sending. It does not auto-end while the client is paused from the Recursos tab.
- There is no «Terminar» in the workspace. Only Android keeps «Terminar captura».
- For burst photos, keep only the chosen shot, downscaled to 2000 px on the long side.
- All UI text is in Spanish.
